# FreeToken sigmoid MoE 路由融合：实验报告与质量风险分析

> 2026-10-21 更新：新增真实提示词前缀/专家输出验证、标准 fixture 测试、基线回归对照和 20 组扩展微基准。最新结果与 PR 就绪性结论见 [本机验收报告](FreeToken-PR-验收报告.md)；本文保留前一轮实验记录。

实验日期：2026-10-20（America/New_York）。状态：本地未提交补丁；未创建 GitHub PR。

## 1. 结论

在 RTX 4060 Laptop GPU 上，现有测试共 **105 项内核测试、6 项模型接入测试通过**。12 组路由微基准中，融合实现耗时降低，对应 **4.049～8.854 倍的局部加速**。

上述结果支持继续推进该优化，但不足以证明完整模型生成速度提升相同比例，也不足以证明生成质量不变。补充的合成输入检查未发现所选专家集合变化，但发现了同分附近的专家顺序变化和很小的权重差异。因此当前结论是：**局部性能收益已验证，端到端质量尚未验证。**

## 2. 目的与实现范围

关联 [Issue #730](https://github.com/FlashML-org/FreeToken/issues/730)。原实现分别调用 PyTorch 完成 sigmoid、选择偏置、可选分组 top-k、权重提取、归一化和缩放。补丁将这些步骤合并为一个 Triton 程序，减少 GPU 启动及中间数据读写。

基本规则为：

```text
原分数 s = sigmoid(logits)
排名分数 = s + bias
按排名分数选择专家；有分组时先选组
输出权重 = 选中专家的原分数 s
按模型配置归一化并缩放
```

偏置不进入最终混合权重。组分数按组内最高两项之和计算。接口返回 FP32 权重和 int32 专家编号。

接入模型：glm4_moe、glm_moe_dsa、glm5_next、minimax_m2、minimax_m3。三个 GLM 的路由权重在原加载完成后转换为 FP32，保留原加载舍入，避免每步重新转换；MiniMax-M2 保留原 gate 路径和零 epsilon；M3 已常驻 FP32。

微基准只测 logits 之后的路由，**没有测量权重转换优化的收益**，也没有测量 GPU 启动次数变化或 profiler 时间线。

## 4. 方法与正确性结果

### 4.1 内核与模型接入

| 检查 | 结果 | 覆盖与限制 |
|---|---|---|
| 内核测试 | 105 passed，21.99 秒 | 含不同形状、FP32/BF16、分组、归一化、缩放、非连续输入、空输入、同分、零和及 CUDA Graph 重放 |
| 模型接入测试 | 6 passed，12.27 秒 | 一个 FP32 路由权重加载测试，以及五个模型 `_route` 的合成数据测试 |

常规对照检查专家编号完全一致，权重使用 `rtol=1e-5, atol=1e-6`。特定零和案例允许对应 NaN；这不是宣称所有输入都保证有限输出。同分专项检查验证新内核“较小编号优先”的规则，不证明与 PyTorch 对所有同分输入等价。

105 是参数化测试用例数，不是模型数量，也不是全部独立随机实验；其中包括空输入检查。内核测试直接加载真实源码，避开服务端包初始化。模型接入测试使用真实模块导入，但部分对象用合成属性构造，未覆盖完整模型构造、checkpoint 加载、专家执行和输出合并。

两组测试通过 `--confcutdir` 绕过仓库全局 fixture，因此不是完整仓库测试套件通过。模型测试在补齐 huggingface_hub、flashlib 等依赖后通过；先前导入失败记录仍保留。

## 5. 补充实验：是否可能影响质量

为区分“数值基本一致”与“输出严格相同”，额外运行 [probe_routing_quality.py](../history/probe_routing_quality.py)。不修改生产补丁，直接执行实际内核。随机种子为 20261020，各案例 1024 行。前四类为 128 专家、top-k=4、无分组；第五类为 192 专家、top-k=8、8 组选 4 组。

| 构造输入 | 专家集合不一致行数 | 专家顺序不一致行数 | 对齐专家后的最大权重绝对误差 |
|---|---:|---:|---:|
| 普通随机 logits，随机 bias | 0 / 1024 | 0 / 1024 | 5.96e-8 |
| 接近同分：logits 标准差 1e-6，bias=0 | 0 / 1024 | 580 / 1024 | 2.98e-8 |
| sigmoid 饱和：logits=20+随机扰动，bias=0 | 0 / 1024 | 1024 / 1024 | 0 |
| 完全同分：logits=0，bias=0 | 0 / 1024 | 1024 / 1024 | 0 |
| 分组完全同分 | 0 / 1024 | 未单独统计；首行顺序不同 | 未单独统计 |

未分组完全同分时，首行原实现返回 `[1,0,2,3]`，新实现返回 `[0,1,2,3]`。两者选中集合相同，但顺序不同。第五类的相同行是重复的同分构造，不应当作 1024 个独立真实样本。

以上实验没有发现专家集合变化，但覆盖面有限，不能把这些比例解释为真实模型的差异发生率。检查的是路由输出，没有计算最终专家加权和、模型 logits 或自然语言回答。原始数据见 [quality-probe-results.json](../history/quality-probe-results.json)。

### 5.1 风险判断

**风险一：同分处理规则不同。** 新实现明确选择较小编号；PyTorch 不承诺 top-k 的同分索引稳定，见 [torch.topk 文档](https://docs.pytorch.org/docs/2.14/generated/torch.topk.html)。本机构造案例目前只是顺序不同；其他形状、设备、版本或分组边界上，仍可能选择不同集合。若选中的专家身份不同，专家输出就可能不同，即使路由分数完全相同。当前不能把这种风险归零。

**风险二：浮点运算差异。** sigmoid 和归约由另一种内核执行，数学表达式相同不保证逐位一致，见 [PyTorch 数值精度说明](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html)。本次已观察到约 1e-8 量级的权重差异。远离选择边界时，这通常只意味着很小的局部变化；在 top-k 或组选择边界附近，微小误差可能改变离散选择。后一种情况在本次有限探针中没有观测到，仍需真实分布验证。

**风险三：顺序变化影响后续浮点累加。** 即使专家集合和每个专家对应权重相同，数学上的加权和相同，实际专家输出的累加顺序也可能改变舍入。是否在 FreeToken 的具体专家后端中产生可见差异，本次没有测量。不能仅凭顺序变化断言质量下降，也不能保证完全无影响。

**风险四：加载和集成覆盖不足。** GLM 权重在加载后转 FP32，设计上保留原数值；一个合成加载测试通过不等于所有 HF/GGUF/FTW checkpoint 路径都已验证。原 bias 精度及上游实现问题也不会因融合而自动修复。此外，全局 fixture、完整专家后端、真实请求调度尚未纳入本轮测试。

**风险五：异常输入范围。** 新内核声明只处理有限 logits/bias；NaN/Inf、极端异常 checkpoint 不在已证明范围。MiniMax-M2 的零和归一化产生 NaN 是保留原语义，不是本次新增的质量修复。

### 5.2 回答“会不会降低质量”

本次没有改模型参数数量、专家数量或量化位宽，目标是执行层面的优化，因此没有主动用质量换速度的设计。但是，**有数值和离散选择边界风险，尚未证明质量无回退**。输出文本不一致也不自动等于质量更差：需要区分计算差异、生成分岔和任务正确率的实际下降。

## 6. 提交前建议补齐的质量验证

1. **真实路由输入回放。** 从受影响模型的实际提示词、prefill/decode 和各层抓取 logits/bias，使用相同输入分别运行两版。分别统计专家集合差异、仅排序差异、权重误差、组选择边界间距，保存差异案例。先研究差异原因，再决定是否需要兼容旧规则或加入特定回退。
2. **固定上下文比较模型输出分布。** 两版使用相同 checkpoint、tokenizer、精度、后端和 token 前缀，比较每步 logits/对数概率。固定输入前缀可以避免首个生成差异让后续比较失去可比性。
3. **任务质量 A/B。** 用固定测试集评价数学、代码、问答等准确率；同时做 greedy 对比和固定配置的多次采样。观察整体与任务分项回退，报告样本量及不确定性，不能只看几个回答是否通顺。
4. **同条件端到端测速。** 在质量对比的相同模型、提示词和设置下记录 tokens/s、TTFT，补齐真实 checkpoint 加载和目标 Linux 环境测试。需要时加 Compute Sanitizer。

在这些结果补齐之前，适合将当前产物称为“已验证局部性能的代码草稿”，不宜写成“完全等价、零质量损失”。

## 8. 追加实验：GLM-4.5-Air 真实路由权重

用户选择先完成本机可做的测试。机器总内存约 31.3 GiB，当时空闲约 15.6 GiB，显存 8 GB；本轮没有尝试完整模型加载或生成。选择实际受补丁影响的 [zai-org/GLM-4.5-Air](https://huggingface.co/zai-org/GLM-4.5-Air)，固定 revision 为 `a24ceef6ce4f3536971efe9b778bdaa1bab18daa`。

通过 HTTP Range 读取 safetensors 中第 1、23、45 层（零起始索引）的 gate 权重和选择偏置；只下载所需字节，未下载完整分片。6 个张量总计 3,147,264 字节，约 3 MiB，不含 config、索引和分片头。数据保存于 `D:/AI/FreeToken-validation/GLM-4.5-Air-router`，记录分片名、字节范围、张量形状、类型和 SHA256。字节校验值用于本地追溯，不表示已经验证整个 checkpoint 的哈希。

真实配置：隐藏维度 4096，128 个专家，每个 token 选 8 个；不分组，归一化开启，缩放为 1。权重为 BF16，选择偏置为 FP32。

| 指标 | 结果 |
